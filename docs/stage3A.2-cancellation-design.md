# Безопасная отмена — технический проект для будущего этапа 3А.2

Статус: документация, реализация и действующая кнопка отмены отсутствуют.

Идентичность собственного задания: Job ID, boot ID, PID, /proc starttime,
зарегистрированные PGID и дерево дочерних процессов. PID без совпадающего starttime
и boot ID никогда не является разрешением послать сигнал. После перезапуска
устройства процессы старой загрузки не считаются живыми. Недоступность /proc
означает UNKNOWN, а не разрешение на уничтожение процесса.

Запрос CANCEL будет отдельным аутентифицированным по сохранённому Job ID запросом,
не shell-командой пользователя. Контроллер атомарно записывает CANCEL_REQUESTED,
фиксирует известные собственные JVM до любого сигнала, проверяет идентичность
непосредственно перед каждым действием. Новые дети регистрируются до exec через
существующий gate. Нужен отдельный контролируемый запуск Gradle daemon, поскольку
он может создать новую сессию и выйти из исходной группы. Общие JVM и чужие
процессы Termux не трогать. Одного killpg недостаточно.

Первое действие — штатное завершение собственного задания. Ограниченное ожидание
и повторная проверка процессов; лишь после этого допускается эскалация для
достоверно принадлежащих этому заданию PID/PGID. Смена идентичности, исчезновение
контроллера, неизвестное происхождение JVM — прекращение эскалации, UNKNOWN.
Частичные очищенные логи и отчёты сохраняются до и после остановки. Итог
CANCELLED допускается только после проверки завершения всех собственных процессов;
иначе UNKNOWN сохраняет блокировку проекта. START автоматически не повторять.

Git SYNC нельзя прерывать в критическом участке обновления рабочего дерева.
Перед разрешением отмены необходимы явные границы стадий и повторная проверка
ветки, SHA, чистоты и состояния Git после остановки. Никаких автоматических
reset/clean/stash/rebase/repair. При сомнениях — UNKNOWN и объяснение владельцу.

Сначала fixture: PID reuse, иной boot ID, /proc denied, detached JVM, появление
ребёнка между проверками, зависшее graceful завершение, чужая JVM, падение
контроллера, повтор CANCEL, поздний callback, сохранность частичного журнала,
различные границы SYNC. Рабочий QuizApp для этих проверок не использовать.
